建议演示顺序：查看模型 → 接收观测 → 查看 RDF 实例 → 运行查询 → 查看地图 → 展示无效数据及验证报告 → 追溯告警依据。距离分级始终明确为距离评价，不能直接等同于综合威胁或违法飞行判断。

本阶段不要求学习推理引擎。距离继续由 Python 计算。先掌握上述标准与开发流程；有真实关系数据库接入需求后，再考虑 Ontop（虚拟知识图谱）和 R2RML（关系数据库到 RDF 的映射）；中文大模型问答放在已有可靠查询与证据链之后。

## ECS 资源判断

此前配置记录为 2 vCPU、2GB 内存、40GB 系统盘；这不是本次实时读数。当前短信明确表示文件备份时磁盘空间不足，不能据此判断 CPU 不够。

此前曾确认 TDB2 物理数据文件约 15GB 导致磁盘满，已恢复并增加定时压缩。逻辑历史条数有限，不代表物理文件自动缩小；压缩也需要临时空间。部署脚本还会保留每次物理数据库备份与镜像，尚无自动保留数量上限。因此扩容必须与保留策略一起实施。

| 使用方式 | 建议配置（工程建议，非性能保证） |
|---|---|
| 只运行本项目，个人学习与偶尔演示 | 2 核、4GB 内存、80～100GB 磁盘；镜像继续在 GitHub Actions 构建 |
| 同时运行多个后端、数据库等服务 | 4 核、8GB 内存、100GB 或更大磁盘，按实测调整 |
| 预算暂不升级 | 保持其他无关服务停止，演示时启动模拟器，治理镜像和备份占用；2GB 内存余量偏小 |

CPU/内存升级不增加磁盘容量；磁盘扩容也不增加内存。具体实例可变配范围与费用以北京地域控制台显示为准，不在本次自动购买或变配。

阿里云文档指出，文件备份客户端及运行缓存占用本机磁盘；运行缓存需要至少 1.5GB 可用空间，低于 1GB 时备份会失败。实际建议保留至少 10GB 或磁盘容量的 20% 作为部署、数据库压缩及备份的余量，文件数量很多时还需额外评估。

## 下次部署前检查与运维改进

在 ECS 执行下列只读检查，先区分容量不足、inode 耗尽、内存压力与备份缓存增长。`du` 可能产生短暂磁盘 IO。

```bash
df -h /
df -i /
free -h
docker stats --no-stream
docker system df
du -xhd1 /opt/airontology /var/lib/docker /opt/alibabacloud 2>/dev/null
systemctl status airontology-maintenance.timer --no-pager
journalctl -u airontology-maintenance.service -n 50 --no-pager
```

改进建议（尚未实施）：

1. 部署前检查磁盘余量：包括上传包、镜像导入、数据库备份和压缩所需空间；不足时停止发布并给出中文原因。
2. 成功验证新版本后，项目发布配置、镜像、备份分别按策略保留，例如最近 2 个可用版本和最近 3 份已验证备份。先列清单再清理，排除运行中版本及其他项目，不使用带 `--volumes` 的全局清理。
3. 检查定时压缩真实执行记录；达到磁盘水位阈值时告警，并考虑暂停模拟器写入，避免再次写满。
4. Docker 日志设置大小与数量限制；备份范围优先覆盖配置和一致性数据库备份。确认阿里云文件备份是否扫描 Docker 镜像、缓存和重复归档，再调整范围。
5. 保留原故障数据归档，确认不再需要后再决定迁移或删除；不直接删除数据库目录或云备份客户端目录。
