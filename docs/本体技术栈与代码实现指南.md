# AirOntology 本体技术栈与代码实现指南

本文帮助你回答两个问题：**项目用了哪些本体技术？这些技术在代码里如何连起来工作？**

以仓库 V2.3 的实现为准。文中的英文都附中文含义，代码中的英文标识保留，方便你在项目里搜索。这里的“已实现”指源码能力，线上 ECS 是否更新需要另行核对部署版本。

## 1. 先看项目真正做的事

系统有两条数据通路，业务前提不同：

| 通路 | 输入前提 | 系统完成的工作 | 不能据此得出的结论 |
| --- | --- | --- | --- |
| 目标航迹演示 | 上游已经给出目标编号与坐标，演示器声明模拟数据 | 算到阵地的距离、分关注等级、保存依据、排序、地图展示 | 不能证明传感器识别出了无人机，距离近不等于综合威胁高 |
| 多源原始证据 | 雷达、无线电、摄像头、红外分别报告观测 | 统一字段，保留来源、时间、误差和原始引用，登记三个层次的待核实判断 | 不会自动把观测合并为同一目标，也不自动确认无人机或未授权闯入 |

本体的作用，是让“设备、观测、目标、阵地、规则、判断及其依据”有明确的含义和关系，可以被查询、检查和追溯。项目没有启用 OWL 自动推理。

## 2. 技术栈一览：每个东西负责什么

| 名称与中文含义 | 在本项目中的职责 | 对应实现 |
| --- | --- | --- |
| RDF，资源描述框架 | 用“主体—关系—客体”三元组表达数据 | `backend/app/domain.py`、`backend/app/evidence.py` |
| Turtle / TTL，RDF 的一种文本写法 | 保存本体定义，交换和显示实例数据；`.ttl` 是文件扩展名 | `ontology/*.ttl`、页面 TTL 查看区 |
| RDFS，RDF 模式词汇 | 中文名称、注释、子类、属性的定义域与值域 | `ontology/cu_ontology.ttl` |
| OWL，Web 本体语言 | 声明类、对象属性、数据属性，表达领域模型 | 同上；没有运行 OWL 推理器 |
| URI，统一资源标识符 | 为概念、设备、观测、判断提供可区分的身份 | `CU` 命名空间、证据 `urn:` 标识 |
| RDFLib，Python 的 RDF 库，固定版本 7.6.0 | 解析 TTL、创建图、添加三元组、序列化 | `domain.py`、`store.py`、`learning.py`、`evidence.py` |
| Apache Jena Fuseki，RDF 查询服务，构建版本 5.3.0 | 提供 SPARQL 查询、更新接口 | `deploy/Fuseki.Dockerfile`、`backend/app/store.py` |
| TDB2，Jena 的磁盘 RDF 存储 | 把 RDF 数据持久化到 Docker 数据卷 | Fuseki 启动参数 `--tdb2 --loc=/data/database` |
| SPARQL，RDF 查询与更新语言 | 按语义关系读取、插入、替换图数据 | `store.py`、`learning.py`、`agent.py`、`evidence.py` |
| Named Graph，命名图 | 按用途隔离定义、当前状态、历史、学习模型和证据 | `urn:airontology:*` 等图名称 |
| SHACL，形状约束语言 | 描述数据结构需要满足的条件 | `ontology/shapes.ttl` |
| pySHACL，Python 的 SHACL 执行库，固定版本 0.40.1 | 执行约束，生成中文问题列表及 RDF 报告 | `backend/app/learning.py` 的 `validate_facts()` |
| Protégé，本体编辑器 | 可选的外部建模工具；编辑模型后导出 Turtle，再导入学习区 | 学习模型预览和隔离导入接口；服务器不运行 Protégé |

以下是配套技术，并非本体标准：

| 技术 | 项目中如何使用 |
| --- | --- |
| Python / FastAPI / Pydantic | 接口、字段校验、业务计算；Pydantic 在入库前检查 JSON |
| pyproj / WGS84 | 按 WGS84 椭球计算水平地表距离，单位米 |
| MQTT / Mosquitto / paho-mqtt | 演示航迹与原始观测的消息接入 |
| Vue 3 / Leaflet / Vite | 页面交互、WebGIS 地图和前端构建 |
| DeepSeek，可选的大语言模型 | 解释已经算好的排序依据；不负责识别、融合或改写事实 |
| Docker Compose / GitHub Actions | 组织容器、验证代码、构建与部署 |

版本以 `backend/requirements.txt`、`frontend/package.json` 和构建文件为准。没有额外引入图数据库、向量库或融合服务。

## 3. RDF 到底怎么表达一件事

普通 JSON 可能写成：

```json
{"id":"drone001", "lon":116.408, "lat":39.9045}
```

RDF 把它展开为带明确身份和关系的语句，例如：

```turtle
@prefix cu: <http://counteruav.org/counterUav#> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

cu:drone001 a cu:BlueDevice ;
    cu:lon "116.408"^^xsd:double ;
    cu:lat "39.9045"^^xsd:double .
```

逐句读：

- `cu:drone001 a cu:BlueDevice`：drone001 被声明为项目中的无人机目标类实例。`a` 是 `rdf:type`（属于哪一类）的简写。类名沿用早期代码，不代表系统已经验证敌我身份。
- `cu:drone001 cu:lon ...`：这个目标有一个经度值。
- `^^xsd:double`：值是双精度数值，不是普通文字。`xsd` 是 XML Schema 数据类型命名空间的常用前缀。
- `;`：下一句沿用同一个主体。`.`：这一组语句结束。
- `cu:`：项目命名空间的简写；它是自定义前缀，不是 OWL 规定的关键字。写 `cu:lon` 就是写完整标识 `http://counteruav.org/counterUav#lon`。

一个三元组的客体可以是另一个资源，也可以是数值、时间、文字等字面值。**RDF 是数据模型；TTL 是把这种模型写成文本的格式。**

URI 用来标识对象，不要求对应网址一定能打开。`urn:airontology:evidence` 也是 URI，是图的名称，不是网页地址。

## 4. OWL 和 RDFS 怎样给数据加上含义

```turtle
@prefix cu: <http://counteruav.org/counterUav#> .
@prefix owl: <http://www.w3.org/2002/07/owl#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

cu:SensorDevice a owl:Class ;
    rdfs:label "传感设备"@zh .

cu:SensorObservation a owl:Class ;
    rdfs:label "传感观测"@zh .

cu:fromDevice a owl:ObjectProperty ;
    rdfs:domain cu:SensorObservation ;
    rdfs:range cu:SensorDevice .
```

这段表示：模型中有“传感设备”和“传感观测”两类对象；`fromDevice`（来自设备）连接一次观测与它的来源设备。

| 写法 | 中文解释 |
| --- | --- |
| `owl:Class` | 类：一种对象的类型，例如设备、观测、判断 |
| `owl:ObjectProperty` | 对象属性：对象之间的关系，例如观测来自某设备 |
| `owl:DatatypeProperty` | 数据属性：对象到数值或文字的关系，例如经度、时间 |
| `rdfs:label "阵地"@zh` | 中文显示名为“阵地”；`zh` 是中文语言标签 |
| `rdfs:comment "说明文字"@zh` | 中文解释或备注；不会自动执行其中的业务规则 |
| `rdfs:subClassOf` | 子类关系，例如雷达设备属于传感设备的一类 |
| `rdfs:domain` / `rdfs:range` | 属性的定义域 / 值域，表达主体、客体所属类型的语义 |

**定义域和值域不等于输入校验规则。** 它们不是数据库外键，也不能理解成“不符合就自动拒绝”。在支持推理的系统里，它们还可能用于推导类型。本项目的拒绝规则由 Pydantic、应用代码及 SHACL 分别承担。

OWL 也用 RDF 三元组表达，所以本体定义与实例事实都可以保存成 TTL。会读 TTL 语法只是第一步，还需要理解 `fromDevice` 等词在领域模型中的含义，以及程序是否执行了推理。

## 5. TBox 和 ABox：定义与实例

TBox 可以理解为“有哪些概念与关系”；ABox 可以理解为“具体有哪些对象与事实”。这是逻辑上的区分，不是两个必然独立的文件格式。

| 层次 | 项目例子 | 代码位置 |
| --- | --- | --- |
| TBox，术语和模型定义 | SensorObservation 是类；fromDevice 是对象属性 | `ontology/cu_ontology.ttl` |
| ABox，具体实例和事实 | 某条观测来自某雷达，观测时间是多少 | `domain.py`、`evidence.py` 生成并写入 Fuseki |
| 约束 | 每条传感观测应有一个来源设备和一个观测时间 | `ontology/shapes.ttl` |

`initial_data.ttl` 中的初始实例与 `attention_policy.ttl` 中的排序策略实例也属于事实数据。虽然初始化时一并装进 schema 图，并不意味着里面每条三元组都是 TBox。**命名图是工程上的分组，TBox / ABox 是含义上的分类。**

## 6. 一条航迹在代码中走了哪些步骤

以模拟器报告 drone001 为例：



1. **生成数据**：`simulator/main.py` 发布 JSON 到 `counteruav/track/blue`，带 `data_mode: simulated`（模拟数据）。
2. **接收和校验**：`consumer.py` 用 `paho-mqtt` 订阅消息；`domain.py` 的 `Track` 检查经纬度、时间、速度等字段。合法报文进入有界队列。
3. **计算距离**：`domain.py` 的 `observation_graphs()` 对每个阵地调用 `GEOD.inv()`。阈值来自运行配置，当前默认 100 / 200 / 300 米。
4. **建立依据链**：同一个函数创建 Observation（观测）、Assessment（评估）和 DistanceRule（距离规则）实例。每个阵地有独立评估。
5. **持久化**：`store.py` 的 `write_track()` 通过 SPARQL Update（更新）写入 Fuseki。旧时间和重复报文不会覆盖最新位置；历史有保留上限。
6. **读取展示**：`views.py` 把图里的数据组装成接口 JSON；前端 `main.js` 和 `template.js` 渲染地图、告警、评估依据、TTL 与回放。

关键关系的简化写法如下，编号仅作教学示意：

```turtle
@prefix cu: <http://counteruav.org/counterUav#> .

cu:drone001 cu:latestObservation cu:obs-example ;
    cu:latestAssessment cu:eval-example .

cu:obs-example a cu:Observation ;
    cu:ofTarget cu:drone001 .

cu:eval-example a cu:Assessment ;
    cu:ofTarget cu:drone001 ;
    cu:basedOnObservation cu:obs-example ;
    cu:toPosition cu:pos001 ;
    cu:usedRule cu:rule-example ;
    cu:hasDistanceLevel cu:HighAttention .
```

“为什么是高关注”可以沿着这些关系找回观测、阵地和当时规则。距离是 Python 算出来的，RDF 保存计算结果与依据，OWL 定义这些对象和关系的含义。**本项目没有用 OWL 推理引擎计算距离。**

## 7. 多源原始观测如何接入

这条通路在 `backend/app/evidence.py` 中，和已有航迹评估分开保存：

1. 先登记 SensorDevice（传感设备），说明雷达、无线电、摄像头或红外，以及状态、覆盖、来源和有效时长。
2. 通过 `POST /api/evidence/observations` 或 MQTT 主题 `counteruav/observation/raw` 提交 SensorObservation（原始传感观测）。主题可以通过环境变量修改。
3. 保存观测时间、服务端接收时间、坐标系、位置及误差、检出结果、质量、特征、原始证据引用。接收时的设备声明也保存快照。
4. 应用代码生成 RDF，并写到独立证据图。相同编号和相同内容可以重复提交；相同编号内容不同会拒绝。观测和判断不能直接覆盖。
5. Judgement（判断）单独引用输入观测、前置判断、方法名称与版本、条件、不确定性和生成时间。

三个判断层分别是：

| 层次 | 要回答的问题 | 本版如何处理 |
| --- | --- | --- |
| association，观测关联 | 这些观测是否可能属于同一目标？ | 登记疑似关系与依据；没有执行融合算法 |
| identification，无人机识别 | 目标是否可能是无人机？ | 单独登记，不能直接继承关联层为身份确认 |
| intrusion，异常闯入条件 | 身份、区域、时间、授权等条件是否满足？ | 登记区域和授权引用；授权未知保持待核实，尚未计算空间包含 |

新通路生成的是 SuspectedTarget（疑似目标），不会自动生成已有航迹通路的 BlueDevice 实例。页面可定位有经纬度的“检出观测”，图标说明它是原始观测；未检出记录不作为目标位置显示。

当前状态提示由 Python 保守检查输入是否过期、设备是否正常、数据声明是否混合、授权是否未知等条件。原登记判断仍保留，不把提示当成识别或融合算法结果。`operational` 只是接入方的业务数据声明，不代表系统已经验证真实能力。

## 8. Fuseki、TDB2 和命名图如何配合

Fuseki 是提供接口的服务；TDB2 是它使用的磁盘存储。应用通过 HTTP 发 SPARQL 请求，数据最终放在 `fuseki-data` Docker 卷中。

| 图标识 | 用途 |
| --- | --- |
| `urn:airontology:schema` | 发布的模型定义、初始等级实例和排序策略实例 |
| `urn:airontology:state` | 目标当前位置与最新观测、评估指针 |
| `urn:airontology:history` | 有界历史观测、独立评估、当时规则快照 |
| `urn:airontology:config` | 当前阵地与运行配置 |
| `http://counteruav.org/counterUav#graph/learning-schema` | 用户在学习区导入的模型，与业务定义隔离 |
| `urn:airontology:analysis` | 最近一次排序分析的事实；不是永久审计历史 |
| `urn:airontology:evidence` | 设备、原始观测、三层判断、区域和授权声明 |

命名图像按用途分的文件夹；它不会自动实现权限控制。`store.initialize()` 在启动时重新加载发布模型，但不清空证据和历史图。学习区导入模型不会改写业务计算代码。

## 9. SPARQL 如何从关系中取数据

在学习工作台中选择预设问题，前端提交查询编号，后端选择固定查询模板。没有把任意用户输入直接当 SPARQL 执行。

以下查询读取原始观测及其来源设备，可在受控的 Fuseki 查询界面中理解或验证：

```sparql
PREFIX cu: <http://counteruav.org/counterUav#>
SELECT ?observation ?device ?time ?outcome
WHERE {
  GRAPH <urn:airontology:evidence> {
    ?observation a cu:SensorObservation ;
      cu:fromDevice ?device ;
      cu:observedAt ?time ;
      cu:detectionOutcome ?outcome .
  }
}
ORDER BY DESC(?time)
LIMIT 20
```

- `SELECT`：选择要返回的列；`?observation` 等是变量。
- `WHERE`：要匹配的关系模式。
- `GRAPH`：明确去哪个命名图查。
- `ORDER BY` / `LIMIT`：排序 / 限制数量。

`store.query()` 接收 SELECT 等查询返回的 JSON 表格；`store.construct()` 用 CONSTRUCT 查询返回 RDF 图；`store.update()` 执行插入、删除等更新。已有学习区的五个固定模板位于 `learning.py`，上述多源查询不是自动加入其中的第六个菜单项。

## 10. Pydantic 与 SHACL 为何都需要

| 检查方式 | 检查对象与时机 | 项目例子 |
| --- | --- | --- |
| Pydantic + 应用检查 | JSON 入库前；检查字段及引用 | 经纬度范围、时间带时区、设备先登记、不能引用不存在的观测 |
| SHACL + pySHACL | 已经形成的 RDF 图；页面点击校验时执行 | 一条传感观测必须有一个来源设备；判断状态只能取允许值；有分数必须有含义说明 |

SHACL 示例：

```turtle
@prefix cu: <http://counteruav.org/counterUav#> .
@prefix sh: <http://www.w3.org/ns/shacl#> .

cu:TeachingObservationShape a sh:NodeShape ;
    sh:targetClass cu:SensorObservation ;
    sh:property [
        sh:path cu:fromDevice ;
        sh:minCount 1 ;
        sh:maxCount 1 ;
        sh:class cu:SensorDevice ;
        sh:message "观测必须来自一个已声明的传感设备"@zh
    ] .
```

意思是：对显式的传感观测实例，检查 `fromDevice` 恰好一个，客体必须符合设备类要求。实际完整约束在 `ontology/shapes.ttl`。

`learning.validate_facts()` 调用 pySHACL，设置 `inference='none'`（不推理），关闭高级与 JavaScript 扩展，不加载 OWL 外部导入。接口返回通过与否、问题对象、问题属性、中文说明，以及报告 TTL。

目前 SHACL 是显式执行的校验功能，**不是所有写入都会自动先执行整图 SHACL**。结构校验通过不证明设备正常、观测真实或算法准确。空图也可能通过，因此页面同时显示校验对象数量。

## 11. 本体是否真的参与了程序运行

有参与，但参与方式需要分清：

- **模型和词典**：OWL / RDFS 定义用于中文术语、类与属性说明、关系展示及模型导入。
- **图查询**：业务数据按 RDF 关系存储，通过 SPARQL 连接观测、评估、阵地与规则。
- **约束执行**：SHACL 描述显式事实约束，pySHACL 生成校验报告。
- **策略读取**：`agent.py` 从 `attention_policy.ttl` 装载的事实中读取排序字段和等级顺序，再由 Python 执行排序。
- **边界**：Python 支持哪些排序字段、如何计算距离与趋势，仍然写在代码中。修改一个中文标签或导入任意 OWL，不会自动产生新算法。

DeepSeek 收到的是已固定的排序摘要，包括数据声明和局限，不直接查询数据库，也不写 RDF。未配置模型时显示规则说明。系统没有使用向量检索、图增强检索生成框架，也没有将大模型回答当作本体事实入库。

## 12. 你可以怎样按顺序学习

1. 打开 `ontology/cu_ontology.ttl`，找 SensorDevice、SensorObservation、fromDevice，先区分“类”和“关系”。
2. 进入“本体学习”查看中文词典，再在“多源观测与证据”点击“导入模拟示例”。所有示例明确标为模拟。
3. 点击“查看证据 ABox TTL”，找到同一观测的类型、来源、时间和检出结果，和页面表格逐项对应。
4. 切换三个判断层，查看它们如何引用同一批观测，以及为什么关联不能直接证明身份或异常闯入。
5. 点击“SHACL 结构校验”，理解检查的是哪些实例和字段；在原有学习区载入异常样例，观察缺少字段后的错误。
6. 阅读 `evidence.py` 的 `save()`，看 JSON 字段如何对应 `out.add((主体, 关系, 客体))`；再看 `store.update()` 如何发给 Fuseki。
7. 最后读 `learning.py` 的固定 SPARQL 模板，以及 `domain.py` 的距离计算，区分“查事实”和“算结果”。

这份项目现在最适合学习的闭环是：**用 OWL / RDFS 定义领域词汇 → 用 RDF 表达实例 → 用 Fuseki / TDB2 保存 → 用 SPARQL 查询 → 用 SHACL 校验 → 用 WebGIS 展示证据。**

后续如果需要 OWL 推理、传感器融合、身份识别或 GeoSPARQL（地理语义查询扩展），应作为独立增量设计、验证与接入。它们目前没有被本项目实现。
